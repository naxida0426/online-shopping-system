# 订单、模拟支付与历史查询

支持下单、模拟支付、取消未支付订单、库存恢复和本人历史查询。后台可以推进已支付订单的发货与完成状态；邮件说明见 [邮件模块](mail.md)。所有交易均为课程模拟。

## 使用流程

1. 登录后从购物车进入 `/checkout`，核对整份清单。
2. 填写收货人、11 位中国大陆手机号和详细地址。课程演示使用虚构信息，地址换行会转为空格。
3. 提交 `POST /orders`。成功返回 303 并进入 `/orders/:id`。
4. 从“我的账户 → 我的订单”查询全部记录，支持订单号、状态筛选，每页 10 笔。详情、支付与取消页面保留返回列表的筛选和页码。

接口不接收商品单价、总价、用户 ID、商品数量或订单状态作为下单依据，只使用当前登录用户的数据库购物车。顾客详情与操作接口对不存在或他人订单均返回 404；管理员只能通过单独受保护的后台路由查看其他用户订单。

## 如何保证数据一致

结算预览在 MySQL 会话中保存随机 UUID 令牌和清单摘要，摘要涵盖条目、商品、数量、名称及单价。收货信息只在提交成功后存入订单，不写入会话。购物车或商品价格变化后，原表单会被拒绝，并展示新清单供用户再次确认。

下单使用同一条连接和一个 InnoDB 事务：

1. 锁定当前用户行，和购物车增改删互斥，避免下单期间新增的数量被误清空。
2. 根据用户与结算令牌查找已有订单，重复提交直接返回原订单。
3. 读取当前购物车，按商品 ID 顺序取得商品排他锁及分类共享锁，重新检查商品状态、分类、库存和金额。
4. 按整数分计算小计和合计，检查 DECIMAL 金额范围及预览摘要。
5. 写入订单，逐项扣减库存并保存商品名称、单价和数量快照。
6. 清空本次用户的购物车，提交事务。任何一步失败均回滚前面的写入。

`orders` 的 `(user_id, checkout_token)` 唯一约束是防重复提交的第二层保障。商品库存更新还带有 `stock >= quantity` 条件。分类共享锁允许不同用户同时读取分类，并在本次事务中阻止分类被停用。锁语法依据 [MySQL SELECT 锁定说明](https://dev.mysql.com/doc/refman/8.4/en/select.html)。

价格、库存或清单冲突返回 409；收货信息不合格或金额超出范围返回 422；CSRF 校验失败返回 403；订单无权访问返回 404。数据库错误沿用公共处理，不向页面输出 SQL、凭据或原始错误堆栈。响应设置 `Cache-Control: no-store`，避免缓存收货信息。

## 状态与当前限制

订单创建后 `order_status=pending`（待确认），`payment_status=unpaid`（未支付），二者独立。库存已在下单时扣减，模拟支付不会再次扣减。

| 操作 | 路由 | 结果 |
| --- | --- | --- |
| 查看支付演示 | `GET /orders/:id/pay` | 只展示，不写支付记录 |
| 模拟支付 | `POST /orders/:id/pay`，outcome=success | confirmed / paid，保存模拟支付单与时间 |
| 取消本次支付 | 同上，outcome=cancel | 订单仍 pending / unpaid，保留库存，支付记录 cancelled |
| 确认取消订单 | `GET /orders/:id/cancel` | 只展示确认页 |
| 取消订单 | `POST /orders/:id/cancel`，confirmCancel=yes | cancelled / cancelled，一次恢复全部库存 |
| 邮件重试 | `POST /orders/:id/email` | 仅本人已支付订单，限次重试 |

支付与取消沿用用户行锁，并锁定本人订单及支付记录。同一订单只保留一条支付记录，取消支付后重试会复用该支付单。重复成功请求返回原状态，已支付订单不能取消，已取消订单不能支付。取消和支付同时提交时只允许一种状态生效。

取消订单按商品 ID 顺序恢复库存，即使商品已下架或软删除也会恢复预留数量，但不会重新上架商品。恢复库存、支付记录及订单状态在同一事务中完成，失败全部回滚。

不支持退款或自动超时关闭；未支付订单需要主动取消。支付表保留当前结果，不记录每次模拟尝试的完整流水。后台只允许已支付订单 confirmed → shipped → completed，不手工伪造支付。

## 验证方式

`npm test` 使用独立 MySQL 测试库，包含正确创建、价格篡改、预览后改价、购物车变化、库存不足、商品失效、跨账号查看、并发重复提交、两人抢最后一件和多商品并发下单。

故障回滚测试只对一次测试连接注入“第二条订单明细写入失败”。前面的订单写入、明细写入、库存扣减及最终回滚都实际在 MySQL 执行，随后查询数据库确认没有残留订单、库存已恢复、购物车保留，再使用同一份表单成功重试。新 Node.js 进程也会读取已保存订单，验证商品改名、改价后历史快照不受影响。

人工演示可按 README 的步骤进行。测试完成后只清理本轮生成的独立测试库记录，不改变运行库商品库存或用户订单。
